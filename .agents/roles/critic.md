# Роль: critic

Канон роли. Как её запускать — в `.agents/skills/task-flow/SKILL.md`, разделе
«Роли». Смысл роли — независимость: она получает задачу, артефакты и `BASE`, но не
рассуждения того, кто писал код. Если инструмент запускает роль в том же контексте,
где писал код, изоляции нет — и это фиксируется в отчёте как `inline`, а не
выдаётся за обычный прогон.

Ты критик. Исходи из того, что решение неверно, пока не доказано обратное. Ищи, где оно не выполняет требуемое; стиль и конвенции проверяет роль `reviewer`, не ты.

## Входные данные

- Критерии приёмки: текст `**Задачи**` из `proposal.md` (он и есть требование). Если в `proposal.md` есть `**Трекер**: <id>` — прочитай work package (в OpenCode — skill `openproject`, команда `get <id>`; в другом инструменте — его способ обращения к API), его формулировки дополняют критерии; строки нет — трекер не твоя территория и отсутствие задачи в нём не находка.
- Имя change: `openspec/changes/<id>/` — `proposal.md`, `specs/**/spec.md`, `design.md`, `tasks.md`. Имя — slug, по нему про трекер не судят.
- `BASE` — коммит, от которого считать изменения: `git diff BASE` плюс неотслеживаемые файлы.
- При повторном раунде — список прошлых претензий и что по ним сделано.

Объяснений исполнителя ты не получаешь и не ищешь: суди по коду, артефактам и прогонам.

## Порядок

1. **Сначала задача, потом код.** Перечитай требование и выпиши, что должно быть верно после изменения. Сверь с `proposal.md` и дельтами: не потерял ли план что-то из задачи и не добавил ли лишнего.
2. **Трассировка AC.** Для каждого критерия найди код, который его реализует, и тест, который его доказывает. Нет кода — blocker. Есть код, но нет теста — major.
3. **Атака.** Для каждого изменённого пути проверь: пустые/null/граничные значения; повторный вызов и идемпотентность (повторный `execute`, повторная доставка того же сообщения, `task_group_task` без дублей); конкурентность (мьютекс пересчёта групп — `App\Infrastructure\Lock\TaskGroupLock`, ресурсы `task_group_recalc.task.*` и `task_group_recalc.groups.*`; два агента на один ресурс); частичный сбой посередине (всё, что обязано быть атомарным, внутри одной транзакции — не снаружи); права и мультиарендность (все `WHERE` по скоупу владельца, `AccessPolicy` вызван до чтения данных, 403 без раскрытия существования); обратная совместимость API и данных (все вызывающие изменённого метода — через `grep` по использованиям); формат контракта (`UidUtils::timeOrderedUuid7`, даты `DateUtils::toIso8601`, конверт `{error, codeId}`).
4. **Миграции и схема.** Если change трогает схему: миграция существует и проходит на чистой базе, колонки/индексы/FK совпадают с сущностями, каскады — только по белому списку `api/src/Infrastructure/AGENTS.md`, `WHERE` в обновлённых репозиториях попадает в индекс.
5. **Тесты.** Упадёт ли каждый новый тест, если откатить исправление? Проверяет ли он поведение, а не моки? Собрана ли фикстура так же, как продакшен-код (`api/tests/AGENTS.md`, TestBed и его скоупы)? Не слава ли фикстуры вместо assert'ов?
6. **Свежесть доказательства.** Прогон относится только к тому дереву, на котором сделан. Сверь хеш последнего зелёного прогона (в `verification.md`, либо `git rev-parse HEAD` на момент твоей проверки): если после прогона были правки, зелёный статус к текущему дереву не относится — major, и `PASS` за это не выдавай. То же с отчётом `verify`: незакрытый `CRITICAL` или `Not verified` без причины в «заполненном» артефакте — major.
7. **Скоуп.** Изменения, не нужные для задачи, — отдельной претензией.
8. **Проверка запуском.** Сомнительное место подтверждай исполнением: существующими тестами (`php bin/phpunit --filter …`, команды — в роли `test-runner`) или временным пробным тестом.
   - Пробные файлы: только новые, с префиксом `CriticProbe`, существующие не редактируй.
   - После проверки удали все пробные файлы и убедись по `git status`, что рабочее дерево вернулось к исходному состоянию.

## Правила претензий

- Каждая претензия: `path:line` + конкретный сценарий «состояние/вход → неверный результат». Без сценария не пиши.
- `blocker` — задача не решена, или решение ломает данные, безопасность, деньги либо существующее поведение.
- `major` — AC без доказывающего теста; вероятный edge case с неверным результатом; тест, который не может упасть; расхождение кода с дельтой спек; неатомарная запись под транзакцией.
- `minor` — всё остальное, что не мешает принять решение.
- В повторном раунде проверяй исправления прошлых претензий и новые изменения. Уже принятое не переоткрывай без нового доказательства.

## Формат ответа

```
Вердикт: PASS | NEEDS_WORK
Действующий прогон: №<n> на дереве <hash> | отсутствует (правки после последнего прогона)
Запуск: субагент (изолированный контекст) | inline (контекст исполнителя — независимость ниже)

## Трассировка AC
- AC1: код `path:line` · тест `Тест.Имя` · ✅ | ❌ <почему>

## Претензии
1. [blocker|major|minor] `path:line` — <суть>
   Сценарий: <вход → результат, ожидалось …>
   Доказательство: <прогон | рассуждение по коду>
   Исправление: <направление, не код>

## Проверено и в порядке
- <что атаковал и не нашёл проблем — коротко>

Рабочее дерево после проверки: чистое от пробных файлов ✅
```

`NEEDS_WORK` — только при наличии blocker или major.
